# 008 上下文与指标

本文说明长任务如何不被上下文窗口限制，以及 Warren 用哪些数字衡量自己做得好不好。前置阅读：[002 循环与恢复](002-loop-and-recovery.md)、[003 运行时](003-runtime.md)。

## 上下文压缩

任务的日志可以无限增长，但发给模型的上下文不行。所以发给模型的是日志的一个**视图**：较早的部分可以被一段摘要代替。

- **何时压缩：**
  - 每次调用模型前估算对话长度（约 4 个字符算 1 个 token）。超过模型上下文窗口的 75% 时先压缩，保留最近约 25% 的原文。
  - 如果模型仍然报"上下文过长"，就压缩并重试一次；连续两次过长才算失败。
  - 窗口大小在每个模型的配置里设（`contextWindow`），不设时按 128K 估算。
- **从哪里切：** 切点一定落在"已发出的每个工具调用都已经有结果"的位置，而且切点之后的第一条不能是工具结果。这样不会把调用和结果拆开，任何提供方都能接受压缩后的请求（`isSafeCut`）。
- **谁来写摘要：** `cheap` 角色的模型。没有配置时，用任务自己的模型。摘要模型拿到的是纯文本转录，长输出已截短，不包含工具定义，所以不会误调用工具。提示词要求它保留做过和验证过的事、决定及其理由、文件和分支的状态、还没解决的错误、用户说过的话和下一步，丢弃可以重新读取的文件内容和命令输出。
- **记进日志：** 写一个 `context.compacted` 事件（摘要内容、替换了多少条、用了哪个模型和多少用量）。状态折叠时按同样方式替换，所以崩溃重启后看到的上下文完全一样。日志本身保留全部原文，界面的回放仍然能看到每一步。
- **成本：** 压缩会让提供方的前缀缓存失效一次。所以只在接近窗口上限时才压缩，平时保持只追加，缓存命中率才高。

## 第三个模型适配器：Anthropic

`packages/model/src/anthropic.ts`，使用官方 `@anthropic-ai/sdk`。

- **消息结构：** 对话转换成交替的 `user` 和 `assistant` 消息；工具调用对应 `tool_use`，工具结果对应 `tool_result`。同一轮的多个工具结果放在同一条 user 消息里。
- **thinking 块：** 原样存进日志（带签名），之后的请求原样发回，这是 API 的要求。其他提供方留下的推理内容会被丢弃。
- **推理强度：** 映射到 `output_config.effort`。
- **缓存：** 用顶层 `cache_control` 自动缓存最长的稳定前缀。
- **错误归类：**
  - 429、5xx（含表示过载的 529）、408、409 可重试，并遵守 `retry-after`；
  - "prompt is too long" 归为上下文过长；
  - SDK 自带的重试关闭，由循环统一决定。

三个适配器跑同一套契约测试（`packages/model/tests/contract.test.ts`）：每个都对着本地的假服务，检查同样的行为。

配置示例：`"hard": { "provider": "anthropic", "model": "claude-opus-5-5" }`，密钥写在 `WARREN_ANTHROPIC_API_KEY`。服务端的拒绝回退（fallbacks）没有启用，需要时可以在适配器里加上。

## 指标

`warren stats`（或 `GET /stats`）从日志汇总以下数字：

| 指标 | 回答的问题 |
|---|---|
| 成功率 | 已结束且不是被取消的任务中，完成了多少 |
| 每个任务的费用中位数和用时中位数 | 一个任务大概要花多少钱、多少时间 |
| 每个任务的平均打扰次数（提问 + 审批） | 它占了你多少注意力（[000](000-philosophy.md) 的核心指标） |
| 缓存命中率 | 只追加的上下文让多少输入 token 由缓存提供 |
| 压缩次数 | 有多少长任务碰到了上下文窗口的上限 |
| GitHub 事件按决定分类，以及观察到的数量 | 推断类规则如果设成 `auto`，会开始多少工作 |

本地演示数据上的一次结果（7 个真实任务，`gpt-6.1-terra` 和 `gpt-6-luna`）：成功率 100%，每个任务的费用中位数 $0.006，用时中位数半分钟，平均打扰 0.3 次，缓存命中率 71%。
