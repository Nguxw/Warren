# 004 测试与验证

本文说明 Warren 如何证明 [002](002-loop-and-recovery.md) 中的恢复设计是对的，以及如何验证不同模型适配器的行为一致。前置阅读：[003 运行时](003-runtime.md)。

## 要证明的性质

对任意崩溃位置和任意次数的崩溃：

1. 任务最终会结束，结果和没有崩溃时一样。
2. 外部动作**恰好执行一次**。

第 2 条由两部分共同保证：

- 循环自己保证"最多一次"：外部调用被崩溃打断后不会自动重跑。
- 模型保证"至少一次"：它被告知结果未知，会先核对再决定是否重试。

## 场景

所有崩溃测试共用一个场景（`@warren/core/testing` 的 `push-scenario.ts`）：读文件，改写文件，push（外部动作），完成任务。场景很小，但包含全部三种副作用等级。

- **模型是确定性策略：** 只根据对话内容决定下一步，所以崩溃后重新请求会得到同样的回答。遇到结果为 `interrupted` 的 push，它会先调用 `check_remote` 查看远端，再决定是否重推，和一个谨慎的真实模型行为一致。
- **工具在产生效果之后、返回结果之前**会调用一次 `afterEffect`。测试在这里制造崩溃，模拟最危险的时刻：效果已经发生，但日志里还没有记录。

## 第一层：内存中的确定性模拟

`packages/core/tests/simulation.test.ts`，在 CI 中运行，耗时约 70 毫秒。

- **`CrashingLog`** 包装内存日志，在第 k 个持久化步骤之后让"进程"死亡。持久化步骤指一次提交（和真实 Store 一样，一批事件原子提交）或一次外部效果。进程死亡后，它的任何读写都会抛出 `Crash`，模拟进程已经不存在。
- **穷举：** 先完整跑一次，得到步骤总数 N。然后对 1 到 N 的每一个 k，在第 k 步之后崩溃一次，重启后跑完，检查不变量。
- **随机：** 用固定种子的伪随机数生成 500 组 1 到 4 次的崩溃序列，失败时可以按种子精确重现。
- **变异检验：** 临时把"外部调用不重跑"改坏，测试立即失败（push 了 2 次）。这说明测试确实在检验这条规则，而不是怎么改都能通过。

## 第二层：真实进程的混沌测试

`evals/chaos/`，手动运行：`bun run chaos [轮数] [种子]`。

- 子进程（`child.ts`）运行真实的守护进程：SQLite（`synchronous = FULL`）、调度器、循环。场景里的"外部世界"存在 `world.json`，用"写临时文件 → fsync → 重命名"的方式原子更新，进程被强杀也不会丢失或写坏，和真实外部系统一样。
- 父进程（`run.ts`）在随机时刻对子进程发 `SIGKILL`，然后重启，直到任务结束。之后读取数据库和 `world.json`，检查不变量。
- 模型和工具带有随机延迟，让强杀分布到启动、模型调用、工具执行和提交的各个阶段。启动阶段被杀时，会留下旧的 `daemon.json`，下次启动要能接管它，这一点也一并被测到。

结果（种子 20261113）：

| 任务数 | SIGKILL 次数 | 打断执行中外部调用的次数 | 不变量违反 |
|---|---|---|---|
| 200 | 519 | 85 | 0 |

## 模型适配器契约

`packages/model/tests/contract.test.ts`：同一套测试分别跑在 OpenAI Responses 和 OpenAI 兼容（Chat Completions）两个适配器上。每个适配器各连一个本地的假 HTTP 服务，服务按对应 API 的格式返回数据。检查的行为：

- 用各自的协议格式发出系统指令和完整对话，包括工具结果。
- 工具调用原样返回参数字符串，并正确读出用量（含缓存命中）。
- 纯文本回复映射为助手消息，停止原因是 `end_turn`。
- 429（含 `retry-after`）、500、401、上下文超长、服务不可达，分别归类为 `retryable`、`retryable`、`fatal`、`context_overflow`、`retryable`。

循环依赖这些行为在所有适配器上一致。新增适配器时，只需要在 `fixtures` 里加一项。

真实接口测试（`WARREN_LIVE=1`）对两个适配器各做一次完整的工具调用来回：Responses 适配器包括加密推理内容的回传；兼容适配器直接连 OpenAI 官方的 Chat Completions 接口。
