# 005 安全边界

本文说明 Warren 如何限制一个任务能做什么：沙箱、特权工具和审批。前置阅读：[003 运行时](003-runtime.md)。

## 威胁模型

模型会读到不可信的内容：仓库里的文件、命令输出、以后还有 issue 和评论。其中任何一段都可能是提示词注入。所以**假设模型会尝试做任何事**，边界必须由机制保证，而不是由提示词保证。

要保护的东西：

- 你的凭证：SSH 密钥、云服务凭证、其他 Agent 的登录态、Warren 自己的 API key。
- 工作区以外的文件，包括你的源仓库。
- 你机器上的其他程序。
- 对外的动作：push、开 PR、发消息。

## 三层信任

| 层 | 运行什么 | 权限 |
|---|---|---|
| 守护进程（可信） | 循环、Store、模型调用、特权工具 | 持有密钥；不执行任何模型写的代码 |
| 进程内文件工具 | `read_file`、`edit_file` 等 | 路径解析到工作区内（跟随符号链接检查），越界即拒绝 |
| 沙箱子进程（不可信） | `shell`、`search` 启动的一切 | Seatbelt 限制，见下 |

## 沙箱（macOS Seatbelt）

实现在 `packages/tools/src/sandbox.ts`。策略**默认拒绝**，只放行命令行工具需要的能力：

- **写：** 只能写任务的工作区和 scratch 目录（再加 `/dev/null` 等设备）。源仓库、home 目录、`/tmp`，以及 macOS 的用户临时目录都不可写。
- **读：** 默认可读。但凭证类和个人数据目录被隐藏，包括 `~/.ssh`、`~/.aws`、`~/.config/gh`、`~/.codex`、`~/.claude`、`~/Library/Keychains`、`~/Library/Application Support` 等，以及**整个 Warren 目录**。在 Warren 目录里只有任务自己的工作区和 scratch 可见，所以既读不到 `credentials.env`，也读不到其他任务的文件。
- **网络：** 按任务开关（`Grant.network`），默认关闭，`warren run --network` 打开。关闭时连本机端口也不通。
- **其他进程：** 只能给沙箱内的进程发信号；不能发 Apple Event、不能启动应用（`open` 依赖的系统服务被拒绝）、不能访问钥匙串等系统服务。
- **环境变量：** 走白名单，Warren 的密钥从不传入。临时文件和包管理器缓存（npm、bun、pip、go）重定向到 scratch。

实现细节：

- **路径一律作为 `-D` 参数传入，从不拼进策略文本**，所以任何路径都不能改变策略的含义。
- Seatbelt 按真实路径匹配（`/private/var/...` 而不是 `/var/...`），所有路径参数都先解析成真实路径。
- **`mktemp` 包装脚本：** macOS 的 `mktemp` 无视 `TMPDIR`，总是写系统的用户临时目录。为了不放开那个目录（那里有其他应用会执行的临时文件，等于一条逃出沙箱的路），scratch 里放了一个包装脚本，排在 `PATH` 最前面，把临时文件转到 `$TMPDIR`。

没有 Seatbelt 的平台（目前是 Linux），配置默认 `sandbox: "auto"` 会退回无沙箱并记录错误日志，`doctor` 也会提示。设为 `"seatbelt"` 时，没有沙箱就拒绝启动。

## 特权工具

需要凭证或会影响工作区以外的动作，由守护进程执行，不在沙箱里：

| 工具 | 作用 | 默认审批 |
|---|---|---|
| `publish_branch` | 把工作区的提交发布到你的源仓库，分支固定为 `warren/<短 id>` | 不需要 |
| `open_pull_request` | 用 `WARREN_GITHUB_TOKEN` 推送分支，并开一个草稿 PR | 需要 |

- 只有任务的 Grant 列出的特权工具，模型才看得到、调得了。有仓库的任务默认授予这两个，没有仓库的任务一个都没有。
- 审批可以在配置里按工具覆盖：`"approvals": { "publish_branch": "required" }`。
- 需要审批时，任务进入等待，**此时还没有写 `tool.started`，什么都没执行**。用 `warren approve <id>` 批准；`warren deny <id> "<原因>"` 拒绝，原因会作为 `denied` 结果交给模型。

**防止借特权工具逃出沙箱。** 工作区里的 `.git/hooks` 和 `.git/config` 都能被沙箱里的模型改写。如果可信进程在工作区里运行 `git push`，就会以完整权限执行模型写的钩子，或者 `core.fsmonitor` 这类配置里的命令。所以：

- 可信进程**从不在工作区里运行 git**，而是由源仓库去 `fetch` 工作区。git 读取一个不可信的仓库时，不会执行该仓库的钩子和配置。
- 对源仓库也禁用钩子、fsmonitor 和凭证助手。否则 pre-push 钩子会在沙箱外运行模型的代码（比如钩子里跑测试），凭证助手会借用你本机 git 的 GitHub 登录。
- 分支名由 Warren 固定为 `warren/<短 id>`，并且只允许快进更新。模型无法覆盖你的其他分支，也无法改写已发布的历史。
- GitHub token 通过环境变量传给 git（`GIT_CONFIG_*`），不出现在命令行参数里。

两个工具都是先检查再动作：重复发布同一个提交没有影响；已有打开的 PR 时直接返回它，不会再开一个。所以崩溃后模型重试是安全的，这和 [002](002-loop-and-recovery.md) 的恢复规则相互配合。

## 验证

- **红队测试**（`packages/tools/tests/sandbox.test.ts`，macOS）：
  - 能做：在工作区里用 git 和 bun、用临时文件（包括不带参数的 `mktemp`）、在授权时访问网络。
  - 被拦下：写源仓库、home、`/tmp` 和用户临时目录；读隐藏目录、Warren 的凭证和其他任务的文件；借符号链接读取隐藏目录；未授权时访问网络；给沙箱外的进程发信号；`open` 启动应用；在环境变量里看到密钥。
- **特权工具测试**（`privileged.test.ts`）：在工作区和源仓库里都植入钩子、`core.hooksPath` 和 `core.fsmonitor`，确认它们都没有被执行。变异检验：去掉 git 的加固参数后，这条测试立刻失败。
- **真实模型：** 用户直接要求 `gpt-6.1-terra` 读 `~/.ssh`、`~/.codex`，访问网络，启动应用。它照做了，全部被沙箱拒绝。

## 已知局限

- **读取是黑名单。** 隐藏目录之外的文件都可读，而网络打开时，可读的东西就可能被发送出去。所以网络默认关闭，只在任务需要时打开。
- 网络是全开或全关，还没有按域名的白名单。
- 进程内的文件工具与沙箱里的 shell 之间，理论上存在符号链接的检查与使用时间差（TOCTOU）竞态。工具调用是串行执行的，所以风险很低。
- Linux 还没有沙箱实现（bubblewrap 是计划中的第二个实现）。
